# 2026-11-28 — feature session (issue #142: per-instance profile of a9ab341 vs Bitwuzla on QF_BV_Smt-2026-11-18; part of #26)

This is a measurement only. Nothing changes in `core/`, `urust/`, `spec/`, `proof/` or `bench/` on
this branch. The instrumentation is on the pushed scratch branch **`agent/2cff1199-profile`**,
which is based on `a9ab341` and is not for merge:

- `7d875ff`: `QFBV_PROF=1` prints the phase times (parse, bridge, translate, lower, normalize,
  elim, blast, SAT, reconstruct) and the search counters (decisions, conflicts, chronological
  backtracks, restarts, reductions, propagations) to standard error.
- `b115575`: `QFBV_DIMACS=path` writes the CNF passed to `dpll` as DIMACS.
- `79db8b7`: per-definition CNF attribution (`blastdef` / `def` lines under `QFBV_PROF`), plus
  **`QFBV_HASH=1`, structural hashing of the Tseitin gates**. AND, XOR and ITE are keyed on their
  normalised inputs, so a gate built twice gets one variable. Without the env var, the CNF is
  byte-for-byte that of `a9ab341`, and tcas60_k_0 and bench_1784 give the same conflict counts.

**Result.** The gap is now **≈ 4 s** (PAR-2 56.0 / 56.4 / 56.2 s against Bitwuzla's 52.6 / 52.0 /
52.3 s). It all comes from **five instances, each spending > 99 % of its time in SAT search**:
+33.5 s together. The other 96 instances are **29.5 s faster than Bitwuzla**: we lose 3.1 s on
small instances and gain 32.6 s, mostly on `brummayerbiere4/unconstrained06/07` (elimination of
unconstrained terms), problem_15 and bench_2443. **There is no fixed per-instance overhead to
recover.** Parse, normalisation and bit-blasting take ≤ 0.14 s on every profiled instance, and
< 5 % of the wall time on all but one.

### What the profile shows

- **tcas60_k_0 is an encoding problem.** 74 multiplications at 49 bits give 221759 of the 228635
  variables. 42 of them are variable × variable (≈ 4700 vars each), and the others have a
  constant operand. Normalisation leaves constant sub-terms as definitions; the blaster folds
  them bit by bit, so that is not the cause. **Structural hashing of the gates (`QFBV_HASH=1`)
  removes the problem.** The CNF shrinks only to 209147 vars, but it becomes **unsat after 3
  conflicts in 0.19 s** of SAT, and the whole run takes 0.4 s in the suite (12 s before).
  Without hashing, the same sub-circuits are built twice with different variables, and the
  contradiction between them has to be found by search. Bitwuzla's AIG manager hash-conses every
  AND.
- **The Sage2 instances do not need a better encoding; their search time is chaotic.**
  - CaDiCaL 2.1.3 (built from source) on *our* CNFs (`QFBV_DIMACS`): bench_1784 51.6 s by default
    and 1.6 s with `--plain`, bench_2404 28.6 / 31.3 s, bench_9019 6.9 / 45.0 s, bench_2443
    43.4 / 6.3 s. On these instances CaDiCaL is often *slower* than our solver.
  - A change of gate input order alone, with the same clauses and literal order inside each
    clause, moved bench_1784 from 7.4 s to 0.96 s and tcas60_k_0 from 10.4 s to 21 s. This was an
    unconditional input normalisation in an early version of the hashing build, since fixed.
  - With hashing, bench_1784 goes 7.7 → 13 s, bench_2443 2.1 → 10.6 s and bench_9019 11.8 → 23.5 s
    (rounds D/E), while bench_2404 goes 6.3 → 3.7 s.
  - Bitwuzla's CNFs for Sage2 are of the same size as ours (12.5k against 10.8k vars).
  - So the 17 s that class (i) loses on Sage2 is run-time variance of an essentially random search
    over CNFs of the same difficulty: a different path, not a slower one.
- **problem_9 is search quality.** The CNFs have the same size (2208 against 2222 vars). CaDiCaL
  `--plain` solves ours in 0.46 s with 10100 conflicts, and its default in 1.68 s with 40831. We
  need 80658 conflicts and 6 s. #140 measured EMA restarts at 2–3 s on this instance.
- **Raw speed is about 2× below CaDiCaL** on the instances where the conflict counts are close:
  maxandminor008 26k against 54k conflicts/s, problem_15 29k against 57k. That is worth ≈ 1–2 s
  of the 3.1 s that class (ii) loses on small instances. The rest of those 3.1 s is word-level
  rewriting: maxandminor008 becomes 83 vars in Bitwuzla, and needs 0.14 s with `-rwl 0`.

## 3. Recommendation (also posted on #26)

1. **Structural hashing of the bit-blaster's gates** (Bitwuzla's AIG manager hash-consing; the
   AIG layer of every bit-blasting solver). It targets **tcas60_k_0: −11 s**, measured 12 → 0.4 s
   in two rounds, and also problem_15 (−2 s) and bench_2404 (−2.6 s). Expected net once Sage2 has
   settled: about −12 to −15 s. **Measured alone it is +12 s** (70.6–71.9 s against 58.3–59.4 s),
   because it moves the three Sage2 instances onto worse paths (+30 s). So it should be issued
   together with item 2, or judged on the broad suite (#67), not on these four instances. For the
   proof, hashing is a memo of `gate_and`/`gate_xor`/`gate_ite` keyed on the input literals; its
   correctness fact is "the memoised literal is equivalent to the gate of those inputs", which the
   CNF semantics of the existing gate lemmas give.
2. **Make the Sage2 search less path-dependent; local-search rephasing (CaDiCaL's W phase,
   `walk`; Kissat's `walkinitially`/rephase W).** All four Sage2 instances are sat with ≈ 11k
   vars. Their times move 1–13 s under changes that do not alter the problem (input order,
   hashing), and Bitwuzla's CaDiCaL with walk solves them in 1.1–5.3 s, except bench_2443 at
   9.0 s. Target: bench_1784, bench_9019 and bench_2404 (+17 s against Bitwuzla now). Expected
   saving: 5–10 s if it brings them to Bitwuzla's level, but the evidence for walk specifically is
   indirect. The prototype should measure each Sage2 instance under 3–4 perturbations (for
   example a shuffled variable order) so that the result is not luck. The alternative for
   problem_9 (−4 s) is EMA restarts in focused mode only on top of the target phase, which #140
   showed works there and fails on Sage2.

Do not spend effort on parse / normalise / blast speed. They take ≤ 0.14 s on every instance
profiled, and the per-instance overhead on the 93 fast instances is already below Bitwuzla's.
