## The variant (uRust subset)

- **Mode flag `stable`.** The search starts in focused mode. It switches at a restart once
  `total ≥ next_switch`. The phases last 1000, 2000, 4000, … conflicts (CaDiCaL's `stabilizeinit`
  = 1000, `stabilizefactor` = 200 %). `switch_inc` stops doubling at 2^30.
  **Unit: conflicts, not ticks.** We have no ticks counter (CaDiCaL counts the cache lines of the
  watch lists it visits). Conflicts are deterministic, already counted (`total`), and easy to bound
  in a contract. CaDiCaL ≤ 1.2 also counted conflicts. A due switch forces a restart. It waits only
  while the trail is at level 0 (`lim.len() > 0`, as for every restart).
- **Focused mode.** It restarts when `conflicts ≥ 2` (`restartint`) since the last restart and
  `fast > 1.1 · slow` (`restartmargin`, as `fast / 11 > slow / 10`). The averages are EMAs of the
  LBD of every learned clause, with α = 0.03 (`emagluefast`) and 1e-5 (`emaglueslow`). They are
  fixed-point `usize` values with 32 fractional bits (`ema_step`), and the glue is capped at
  2^20. CaDiCaL corrects the bias of an EMA that starts at 0, which needs a division by
  1 − (1−α)^t. Here the weight is instead 1/(t+1) while t + 1 < 1/α (a running mean), and α after
  that. This gives the same effect without that division. Like CaDiCaL's `swap_averages`, the
  EMAs are updated only in focused mode, so stable mode leaves them unchanged. Decisions take the
  saved phase only. The restart does not swap the two activity orders (that would happen every few
  conflicts) and does not rebuild the heap.
- **Stable mode.** It behaves exactly as `a9ab341`: Luby·100 restarts and the target phase in
  decisions. A restart swaps the activity orders. The Luby index `lu` restarts at 0 each time the
  search enters stable mode, as CaDiCaL resets `reluctant`. When `MODES = false`, `lu` is the same
  as `restarts` and the build behaves as `a9ab341`.
- The target and best phases are kept in both modes, and rephasing is unchanged. Only the use of
  the target phase in decisions depends on the mode, as with CaDiCaL's `target = 1`. No parameter
  was tuned on an instance.

Extra variant, not asked for: **modes, target in both modes** (decisions take the target phase in
focused mode too, so only the restart policy alternates; a scratch edit, not committed). It shows
that the restart policy and the target phase have separate effects:

- **EMA restarts help the calypto instances.** problem_9 and problem_15 drop from about 6 s to
  2–4 s in every build that has focused mode, with or without the target phase.
- **Without a target phase, the Sage2 models get lost.** Focused only times out on three of the
  four Sage2 instances. In the mode switch, the stable phases are short at the start (2000 and
  then 8000 conflicts, after 1000 and 4000 focused ones), and bench_2443 and bench_9019 both get
  much slower. bench_2404 and bench_1784 get faster, so the effect depends on the instance's path.
- **EMA restarts with the target phase are worse than Luby on Sage2.** In the "target in both"
  variant, every Sage2 instance takes 15–24 s. The target phase is the largest conflict-free
  trail *since the last restart*, and focused mode restarts every few conflicts, so the target
  phase is almost always empty or short there.
- tcas60_k_0 is order-sensitive (#81, #124, #132). It times out with the mode switch and takes
  9–10 s with the target in both modes. Read it as noise around a real cost, not as a property of
  one build.

None of the variants comes near `a9ab341`. Without tcas60_k_0, the mode switch is still about
20 s worse (≈ 64–70 s against ≈ 45–48 s), mostly through bench_2443 and bench_9019.

## Proof obligations for a later `dpll` contract (compared with #108 / #124 / #132)

The mode switch does not change the clause database, the watches, the reasons or the trail
structure. It changes when a restart happens and the sign of a decision. The restart branch has
the same shape as before: it backtracks to level 0 and keeps `restarts < 2^20`. So the obligations
of #108/#124/#132 stay as they are, and the restart branch no longer depends on `budget` for
safety. New, all of them local:

- **EMA state.** `ema_step` must not overflow and must keep the invariant `ema_fast, ema_slow ≤
  2^52` (start 0). The new value lies between `e` and `y1`, where `y1 ≤ 2^52` because of the glue
  cap, so the bound holds by induction. Then `(y1 − e) · 3 < 2^54`, and the divisors `t + 1`,
  `100`, `100000` are positive. `ema_t ≤ 2^20` (guarded), so `t + 1` cannot overflow. The restart
  test divides instead of multiplying, so it has no overflow. No fact about the EMA values is
  needed for correctness: they only choose *when* to restart.
- **Mode flag.** `stable` is a `bool`, and it does not occur in any invariant. A decision of
  either sign keeps the invariants (#69), so it does not matter that `stable` picks between
  `tph[v]` and `ph[v]`. The bounds `v < length tph` and `v < length ph` are those of #132 and #69.
- **Switch counters.** `switch_inc ≤ 2^31` (it doubles only while `< 2^30`). `next_switch = total
  + switch_inc` needs `total` bounded, which is the same open point as #108/#132 (`next_reduce`,
  `next_rephase`): bound `total` like `restarts`, or use `saturating_add`. `lu ≤ restarts < 2^20`
  bounds `luby(lu)` and `100 · luby(lu)` as before. Fuel `3 ^ n` is unchanged.

## What remains

- Do not stack the mode switch onto `a9ab341`. If it is tried again, it needs more than CaDiCaL's
  defaults on this solver. Two things to try are trail reuse at focused restarts (CaDiCaL's
  `restartreusetrail`, which keeps the trail that the frequent restarts would otherwise rebuild)
  and the target phase kept across focused restarts. Both are design changes, not default
  settings, so they need a new issue from the planner.
- The calypto gain from EMA restarts (6 → 2–4 s) is real in every build that has them. It is
  small in PAR-2 (about 6 s) and comes with large Sage2 losses.
